# 虚拟人物陪伴系统项目计划书

## 1. 项目定位

虚拟人物陪伴系统是一个本地运行的角色陪伴项目。

它的核心目标是让用户和虚拟人物进行连续、可调整、有记忆感的对话。
系统不追求公开服务，也不以商业化部署为当前目标。

项目更关注以下问题：

- 人物设定如何稳定生效。
- 对话如何体现角色性格和说话方式。
- 用户如何发现并修正人设偏差。
- 多个人物如何以独立角色包方式维护。
- 本地数据如何安全保存。

## 2. 目标用户和使用场景

当前目标用户是本地个人用户和开发者。

主要使用场景包括：

- 与虚拟人物进行日常文字聊天。
- 测试不同人物的性格、语气和反应方式。
- 通过反馈持续调整角色人设。
- 保存长期聊天记录，观察人物表现变化。
- 可选使用语音能力，生成角色回复音频。

后续可以扩展到日程陪伴、日记阅读和更完整的共享关系记忆。

## 3. 当前已实现能力

当前系统已经具备以下能力：

- 本地单用户登录保护。
- 普通角色聊天接口。
- 聊天记录保存到 PostgreSQL。
- 人物角色包集中管理。
- 角色列表、详情、创建、更新、删除、恢复。
- 角色头像上传。
- 角色包校验。
- 人设反馈记录。
- 人设编辑 AI 多轮讨论。
- 最终人设修改方案生成。
- `preview_character_json` 预览。
- 用户确认后应用人设修改。
- 人设上一版备份和回滚。
- 可选 GPT-SoVITS 语音接口。
- 人物系统 debug 接口。
- 人物包 CLI 工具。

## 4. 当前技术架构

后端使用 FastAPI。

数据库使用 PostgreSQL，主要保存聊天、记忆、知识库、反馈和本地用户数据。

前端当前是 `frontend/simple_web` 下的轻量网页。

人物相关文件集中在：

```text
backend/modules/characters/
```

默认人物包在：

```text
backend/modules/characters/packs/role01/
```

人设编辑、普通聊天、检索和语音配置都应通过人物模块读取角色包。

## 5. 模块化设计原则

项目采用按业务模块拆分的方式。

每个模块应尽量只管理自己的业务边界：

- `auth` 管理登录。
- `chat` 管理普通聊天。
- `characters` 管理人物角色包。
- `persona_review` 管理人设编辑闭环。
- `memory` 管理长期记忆。
- `knowledge` 管理知识库。
- `voice` 管理语音调用。
- `debug` 管理调试接口。

新增功能优先放入对应模块。
不要让多个模块到处拼接人物包路径。

## 6. 人物系统设计

人物系统集中在 `backend/modules/characters`。

公共模板在：

```text
backend/modules/characters/templates/
```

每个角色一个独立目录：

```text
backend/modules/characters/packs/{character_id}/
```

角色目录内通常包含：

```text
character.json
voice_refs/
backups/
```

`character.json` 是唯一必需文件。

`voice_refs/` 保存本角色的本地语音参考素材。

`backups/` 保存上一版人设文件，用于回滚。

`.trash/` 用于安全删除后的角色包暂存。

旧目录 `backend/data/character_packs` 已废弃，不再作为新增人物位置。

## 7. 人设编辑闭环

人设编辑流程分为四步：

1. 用户选择聊天片段并写下评价。
2. 系统调用人设编辑 AI 讨论修改方向。
3. 系统生成最终修改方案和 `preview_character_json`。
4. 用户确认后才写入 `character.json`。

其中：

- `chat` 只讨论，不写文件。
- `finalize` 只生成预览，不写文件。
- `apply` 才写入角色包。
- `rollback` 只恢复上一版备份。

人设写入前必须校验角色包。
写入失败不能覆盖原始 `character.json`。

## 8. 数据保存和数据安全

系统数据主要分为两类：

- 数据库数据。
- 人物包文件。

数据库保存聊天、记忆、知识库、反馈和用户相关信息。

人物包保存角色设定、示例对话、反应规则、语音配置和头像地址。

安全原则：

- 不提交 `.env`。
- 不提交真实私人聊天数据。
- 不提交官方素材、语音、模型权重。
- 删除角色时移动到 `.trash`。
- 不永久删除历史聊天。
- 人设修改前保留上一版备份。

## 9. 可选语音能力

语音能力不是核心依赖。

如果配置了 GPT-SoVITS 服务，系统可以将角色回复转换为语音。

角色语音配置保存在 `character.json` 的 `voice` 字段中。

如果配置了 `ref_audio_path`，路径应能在当前角色包目录下正确解析。
如果配置参考音频，也必须提供对应的 `prompt_text`。

语音服务不可用时，普通文字聊天仍应保持可用。

## 10. 未来功能规划

后续可以逐步推进以下方向：

- 更完整的角色管理前端。
- 多人物创建、复制、导入和导出。
- 日程管理。
- 日记系统。
- 共享关系记忆。
- 更完善的长期记忆摘要。
- 更细的人设变更审计。
- 语音素材管理界面。
- 多模型后端适配。

这些功能应在现有模块边界内逐步实现。

## 11. 开发阶段规划

第一阶段：稳定当前本地聊天和人物包读取。

第二阶段：完善人物系统模块化，保证创建、删除、恢复和校验可靠。

第三阶段：完善人设编辑闭环，让反馈能稳定转化为可审查的人设修改。

第四阶段：增强长期记忆、知识库和共享关系记忆。

第五阶段：按需加入日程、日记和更丰富的陪伴能力。

第六阶段：优化前端角色管理体验和调试工具。

## 12. 风险和约束

当前项目仍以本地个人使用为边界。

主要风险包括：

- 人设修改可能破坏角色一致性。
- LLM 输出可能不稳定。
- 语音服务依赖本地环境。
- 私人聊天数据需要谨慎保护。
- 多人物管理需要避免路径混乱。
- 旧目录和旧服务引用需要持续清理。

开发约束：

- 不恢复模拟 provider 或隐藏错误的旧路径。
- 不静默吞掉角色包错误。
- 不绕过人物模块读写角色包。
- 不让 `chat` 或 `finalize` 直接写入人设文件。
- 不提交私人数据、素材和模型权重。
